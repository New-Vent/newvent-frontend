# 백엔드 실측 현황 — 프론트가 맞춰야 할 것

**작성 2026-09-29 · 백엔드 `develop`(`da2380e`, PR #73 머지 직후)을 로컬에 띄워 `curl` 로 확인.**

## 방침

**백엔드 실제 동작이 정답이다. 프론트가 거기에 맞춘다.**

`docs/API.md` 는 프론트가 백엔드에 낸 *제안*이었다. 어긋나는 곳은 제안을 접고
프론트를 고친다. 프론트가 어떻게 해도 안 되는 것만 협의 대상으로 남긴다.

범위는 **배포 없이 로컬에서 API 연동**하는 것까지다. nginx + certbot 은 별도 작업이다.

---

## 이미 통과한 흐름

DB(docker) + 백엔드(`bootRun`) + Vite 만으로 끝까지 돈다. EC2·nginx·DuckDNS 불필요.

```
POST /auth/admin/login             200   accessToken + Set-Cookie: refresh_token; Path=/auth
GET  /api/admin/events             200
GET  /api/admin/templates          200   5종
POST /api/admin/events             200   DB 에 저장됨 (PR #73 으로 JPA 전환 완료)
POST /api/admin/events/{id}/generate  202  jobId
GET  .../generate/{jobId}          QUEUED(0) → VALIDATING(80) → DONE(100), versionId
GET  /api/admin/events/{id}/preview   200  완성된 HTML
```

**로그인 계정** (`V7__set_dummy_passwords.sql`): 관리자 `admin` / `admin1234!`,
사용자 `user01`~`user19` / `user1234!`

폴링 계약(`phase`·`label`·`percent`·`done`·`versionId`)은 기대대로 내려온다.

# A. 프론트가 고친다

## A-1. 응답 봉투를 벗겨야 한다 ★ 가장 광범위

성공은 봉투에 싸여 오고, 실패는 최상위에 온다.

```jsonc
// 성공 (ApiResponse)
{ "success": true, "data": { … }, "message": null }

// 실패 (ErrorResponse)
{ "success": false, "code": "AUTH401-0",
  "message": "아이디 또는 비밀번호가 올바르지 않습니다.",
  "timestamp": "2026-09-29T17:18:39.815948" }
```

`api.js:167` 은 `res.json()` 을 그대로 돌려준다. 호출자가 `{success, data, message}`
를 받게 되므로 **모든 호출부가 한 겹 잘못 읽는다.**

오류 경로(`api.js:159-164`)는 `.json()` 의 `message` 를 읽으니 우연히 맞다. 그대로 두면 된다.

→ `raw()` 를 감싸는 쪽에서 **한 곳만** 고치면 된다. 호출부는 안 건드린다.

```js
const body = await res.json()
if (body.success) return body.data
throw new ApiError(body.message, res.status, body.code)
```

> **실패 응답의 `success: false` 는 백엔드 브랜치 `refactor/error-response-envelope`
> 에서 추가했다 (머지 대기).** 원래는 실패에 `success` 필드가 아예 없어서
> `body.success === false` 로 판별할 수 없었고, HTTP 상태로 먼저 갈라야 했다.
> 머지 전이라면 `if (res.ok)` 로 갈라 두고, 머지 후 위 코드로 바꾸면 된다.
> `code` 는 프로그램적 분기용이니 토스트에는 `message` 만 쓴다.

## A-2. 인증 경로에 `/api` 가 없다

| 프론트 현재 | 백엔드 실제 |
| --- | --- |
| `/api/auth/*` | `POST /auth/login` |
| `/api/admin/auth/*` | `POST /auth/admin/login` |
| | `POST /auth/refresh` |
| | `POST /auth/logout` |

`AuthController` 의 `@RequestMapping("/auth")` 다. 사용자·관리자가 **같은 `/auth` 아래**에
있고, 관리자는 `/auth/admin/login` 으로 갈린다.

⚠️ `/api/auth/login` 을 부르면 **404 가 아니라 401** 이 온다. 컨트롤러가 없어서
`SecurityConfig` 의 `/api/**` → `hasAnyRole` 규칙에 먼저 걸리기 때문이다.
"비밀번호가 틀렸나" 로 오해하지 말 것 — 경로가 없는 것이다.

→ `createApi({ authBase })` 구조가 흔들린다. refresh·logout 은 양쪽 모두 `/auth` 이고
**로그인 경로만** 갈리므로, `authBase` 와 `loginPath` 를 분리해서 주입하는 편이 깔끔하다.

## A-3. Vite 프록시에 `/auth/` 를 추가

A-2 를 고쳐도 `vite.config.js` 의 `proxy` 가 `^/api/`·`^/e/` 만 넘기므로
`/auth/login` 은 Vite 가 정적 파일로 찾아 **404** 가 난다.

```js
const proxy = {
  '^/api/':  { target: API_TARGET, changeOrigin: true },
  '^/auth/': { target: API_TARGET, changeOrigin: true },   // ← 추가
  '^/e/':    { target: API_TARGET, changeOrigin: true },
}
```

## A-4. 토큰 만료 필드가 절대시각이다

```jsonc
{ "accessToken": "…", "expireDate": "2026-09-29T08:01:20.780926Z" }
```

`api.js:93` 은 `setToken(data.accessToken, data.expiresIn)` — **초 단위 상대값**을
기대한다. 백엔드는 `expireDate`(ISO-8601 절대시각, UTC)를 준다. 이름도 의미도 다르다.

A-1 의 봉투 문제까지 겹쳐서 지금 코드로는 `data.accessToken` 이 `undefined` 다.
**refresh 가 토큰을 null 로 만들어 즉시 로그아웃 루프에 빠진다.**

→ `setToken` 이 절대시각을 받게 바꾸거나 `Date.parse(expireDate) - Date.now()` 로 환산.
`jwtExpiry()` 폴백이 있어 죽지는 않지만 의도한 경로가 아니다.

## A-5. 공개 조회는 `/api/public/events`

| 프론트 현재 | 백엔드 실제 |
| --- | --- |
| `/api/events` | `GET /api/public/events` |
| `/api/events/{id}` | `GET /api/public/events/{id}` |

`SecurityConfig` 가 `/api/public/**` 를 통째로 열지 않고 공개할 것만 하나씩 적는
방식이라(의도된 설계다), `/api/events` 는 **401** 이 온다.

## A-6. SSE 를 폴링으로 바꾼다 ★ 작업량 큼

`EventSource` 가 `api.js`·`repo.js`·`editor-state.js`·`views/editor.js` 에 걸쳐 있다.
백엔드에 SSE 엔드포인트는 **없다.** `jobId` 폴링이다.

```
POST   /api/admin/events/{id}/generate          → 202 { jobId, phase, percent }
GET    /api/admin/events/{id}/generate/{jobId}  → { jobId, phase, label, percent,
                                                    done, attempt, message, versionId }
DELETE /api/admin/events/{id}/generate/{jobId}  → 취소
POST   /api/admin/events/{id}/edit              → 채팅 수정. 같은 jobId 폴링을 쓴다
```

`phase` 전체: `QUEUED` `PREPARING` `ROUTING` `CALLING` `VALIDATING` `SAVING`
`DONE` `FAILED` `ASK_BACK` `CANCELLED`

**★ `ASK_BACK` 을 반드시 따로 다뤄야 한다** (채팅 수정 기능)

`done == true` 지만 **실패가 아니다. 되묻기다.** `message` 에 관리자에게 던지는
질문이 들어온다 — `FAILED` 일 때의 오류 문구와 **같은 필드**를 쓴다.

```js
if (!s.done) continue
if (s.phase === 'ASK_BACK')      showQuestion(s.message)   // 빨간 실패가 아니다
else if (s.phase === 'FAILED')   showError(s.message)
else if (s.phase === 'DONE')     loadVersion(s.versionId)
```

`done` 만 보고 성공/실패로 갈라면 되묻기가 빨간 "실패" 로 뜬다.
`ROUTING`(20%, "요청을 이해하는 중")은 수정 흐름에서만 나타나는 단계다.

**★ 수정 작업도 폴링은 `/generate/{jobId}` 로 한다.** `POST .../edit` 으로 시작하고
`GET .../generate/{jobId}` 를 읽는다. 경로 이름이 오해를 부르지만 의도된 공유다.

`api.js` 주석의 "SSE 스트리밍 중에는 401 재시도가 통하지 않는다" 를 근거로 만든
`ensureFresh()` 사전 갱신은 폴링에서는 근거가 사라진다. 요청마다 401 재시도가 그냥 된다.

## A-7. 리프레시 쿠키는 하나다

```
Set-Cookie: refresh_token=…; Path=/auth; Max-Age=604800; Secure; HttpOnly; SameSite=Lax
```

`API.md` 가 제안한 `nv_user_rt`(Path=`/api/auth`) + `nv_admin_rt`(Path=`/api/admin/auth`)
2개 구조가 아니다. 이름 하나·Path 하나를 사용자·관리자가 공유한다.

→ 프론트는 HttpOnly 쿠키를 직접 읽지 않으니 코드에서 지울 건 없다. `API.md` 의 해당
서술을 고치고 refresh 경로를 `/auth/refresh` 하나로 통일하면 된다.
**단, 여기서 파생되는 제약은 C-1 협의 대상이다.**

## A-8. 템플릿 코드에 `template_N_` 접두사를 붙여야 한다 (임시 대응)

| `GET /api/admin/templates` 가 주는 `templateKey` | `POST .../generate` 가 받는 `templateCode` |
| --- | --- |
| `sports_cheer` | `template_1_sports_cheer` |
| `holiday_gift` | `template_2_holiday_gift` |
| `member_appreciation` | `template_3_member_appreciation` |
| `flash_sale` | `template_4_flash_sale` |
| `pre_registration` | `template_5_pre_registration` |

목록에서 고른 값을 그대로 넘기면 **100% `GEN400-2`**("선택한 템플릿을 찾을 수 없습니다").
실측으로 확인했다 — 접두사를 붙이면 202 가 온다.

목록 API 는 `event_templates` 테이블(`V8` 이 `sports_cheer` 로 시드)을,
생성 API 는 `src/main/resources/templates/templates.json`(`template_1_sports_cheer`)을 본다.

→ 위 5개 매핑표를 한 곳에 두고 generate 호출 직전에 변환한다.
**번호를 순서로 유도하지 말 것** — 템플릿이 추가되면 깨진다. 명시적인 표로 둘 것.

백엔드에 이슈로 올려뒀다. 통일되면 매핑표를 지운다. 임시 코드라는 주석을 남길 것.

## A-9. 아직 없는 기능은 숨긴다

| 프론트가 부르는 것 | 백엔드 |

# B. 백엔드 쪽 항목

- **응답 봉투 비대칭** (A-1) — **고쳤다.** 브랜치 `refactor/error-response-envelope`,
  머지 대기. 실패 응답에 `success: false` 가 실린다
- **템플릿 코드 어휘 통일** (A-8) — 이슈로 올렸다. 프론트가 매핑표로 임시 대응 중
- **404·405·타입 불일치가 500 으로 나간다** — 아래 참고

없는 경로, 잘못된 HTTP 메서드, `{id}` 에 숫자가 아닌 값을 넣으면 전부
`500 COMMON500-0` "서버 내부 오류가 발생했습니다" 가 온다. `GlobalExceptionHandler`
의 `@ExceptionHandler(Exception.class)` 가 `NoResourceFoundException`,
`HttpRequestMethodNotSupportedException`, `MethodArgumentTypeMismatchException` 을
같이 삼키기 때문이다.

```
GET  /api/admin/없는경로     → 500 COMMON500-0   (404 여야 한다)
PUT  /api/admin/events       → 500 COMMON500-0   (405 여야 한다)
GET  /api/admin/events/abc   → 500 COMMON500-0   (400 여야 한다)
```

프론트 입장에서 **경로 오타가 서버 장애로 보인다.** 디버깅할 때 이걸 모르면
백엔드가 죽은 줄 알고 헤맨다. 고쳐질 때까지는 500 을 받으면 경로·메서드부터 의심할 것.

# C. 협의가 필요하다

## C-1. 사용자·관리자 동시 로그인이 안 된다

리프레시 쿠키가 이름 하나(`refresh_token`)·Path 하나(`/auth`)뿐이라
**쿠키 슬롯이 하나다.** 관리자로 로그인하면 사용자 세션이 덮어써진다.

사용자 화면과 관리자 화면이 같은 도메인에 있으니 실제로 부딪힌다.
"사용자 로그인 / 관리자 로그인 분리" 요구사항과 어긋나는 지점이다.

프론트는 HttpOnly 쿠키를 건드릴 수 없어 코드로 해결할 방법이 없다. 선택지는 둘이다.

1. **백엔드가 쿠키를 둘로 쪼갠다** — 이름·Path 를 사용자/관리자로 분리
2. **제약을 받아들인다** — 한 브라우저에 한 쪽만 로그인. 관리자는 시크릿 창을 쓴다

데모에서 관리자와 사용자를 번갈아 보여줄 계획이면 1번이어야 한다.
**백엔드 인증 담당자와 결정할 사항.** 이슈로 올렸다.

# 로컬 연동 실행 절차

배포 없이 된다. 백엔드 레포에서:

```bash
docker compose up -d                      # postgres
set -a; . ./.env; set +a
export DB_URL="jdbc:postgresql://localhost:5432/$DB_NAME"
sh gradlew bootRun                        # gradlew 에 실행권한이 없어 sh 로 부른다
```

Flyway 가 V1~V9 를 적용하면서 더미 관리자·사용자·템플릿 5종·이벤트 7건까지
다 넣어준다. 별도 시드 작업이 필요 없다.

프론트: `npx vite`(사용자 5173) / `npm run dev:admin`(관리자 5174).
백엔드 `.env` 의 `LLM_PROVIDER=mock` 이면 Bedrock 을 부르지 않아 비용이 0 이다.

# 별개 작업 — nginx + certbot

이 문서는 **로컬 연동** 범위다. 배포 세팅은 따로 진행한다.
다만 아래 둘은 물려 있으니 배포 작업할 때 같이 봐야 한다.

- `deploy/nginx/newvent.conf` 에 **`location /auth/` 가 없다.** A-2·A-3 과 같은 누락이다.
  `location /api/` 블록을 복사해서 하나 더 만들어야 로그인이 된다.
- `location /e/` 는 있는데 백엔드에 컨트롤러가 없다(A-9). 배포해도 401 이다.

`newvent.duckdns.org` → `54.116.77.235`(EIP) 해석 확인됨. `server_name` 도 일치한다.

> **`docs/API.md` 의 `server.forward-headers-strategy` 경고는 이 코드베이스에서는
> 성립하지 않는다.** 실측으로 확인했다 — `AUTH_COOKIE_SECURE=true` 로 띄우고 평문
> HTTP 로 로그인해도 `Set-Cookie: …; Secure` 가 그대로 붙는다. Spring 의
> `ResponseCookie.secure(true)` 는 요청 스킴을 보지 않고 속성을 그대로 쓰기 때문이다.
> 백엔드에서 요청 스킴을 읽는 코드도 없다(`CsrfOriginFilter` 의 `getScheme()` 은
> **Referer 헤더**를 파싱하는 것이라 무관하다). 리다이렉트 URL 을 만들거나
> `isSecure()` 로 분기하는 코드가 생기면 그때 넣으면 된다.
